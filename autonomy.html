3.2 Utiliser les crédits disponibles

Le mode de financement prévoit des crédits API promotionnels éligibles. L’offre liée à ChatGPT Pro/Business couvre notamment Responses, Agents et leurs outils facturés dans l’organisation liée ; elle exclut Codex utilisé avec une clé API. Le moteur est donc remplacé par un agent utilisant directement Responses API. Voir les conditions de l’offre.

La politique est conservée dans .github/autonomy/budget-policy.json, avec le plafond de 10 € par mois de dépenses réelles. Elle ne constitue pas un contrôle financier appliqué par le programme. La première sonde vérifiera l’inférence avec la clé existante ; le solde applicable doit appartenir à son organisation. Aucun nouvel achat n’est nécessaire avant cette vérification.

Le worker n’achète et ne recharge jamais de crédits. Un refus API provoque une pause, sans tentative automatique répétée. Si un plan API payant est ajouté ultérieurement, vérifier d’abord un blocage de dépenses avec une marge pour la conversion, les taxes et le délai de propagation éventuel. Les alertes seules ne bloquent pas les requêtes. Voir les limites de dépense.

3.3 Cycle d’une session

~{mermaid} flowchart TD S[“Déclenchement manuel ou horaire”] –> E[“Relire l’état et les tickets”] E –> G{“Financement et activation validés ?”} G –>|non| A[“Aucun appel au modèle”] G –>|oui| T[“Réserver une session et choisir un ticket”] T –> R[“Responses API”] R –> C[“Conteneur isolé : code, tests et preuves”] C –> J[“Résultat JSON : fichiers texte complets”] J –> V[“Job GitHub distinct : valider et publier une PR”] V –> I[“Research checks sur le SHA exact”] I –>|succès| M[“Fusion si les règles GitHub l’autorisent”] I –>|échec| F[“Réparation bornée ou pause”] M –> P[“Publier le livre et mettre à jour le ticket”] F –> N[“Bref message Telegram si utile”] P –> N ~

Le contrôleur est dans .github/autonomy/worker.py et le client du modèle dans .github/autonomy/responses_agent.py. La réservation précède l’appel au modèle. Les écritures GitHub, l’appel au modèle et Telegram restent dans des jobs séparés.

La sonde et la planification n’ouvrent aucun conteneur. Pour une tâche de code, GitHub prépare un export de HEAD avec git archive et des wheels Python 3.11 pour les dépendances CPU. Les fichiers non suivis, l’archive brute, les poids et les secrets d’environnement ne sont pas inclus dans cet export. Un manifeste conserve les empreintes de la source et des wheels.

Le paquet est temporairement envoyé à OpenAI, puis monté dans un conteneur de 1 Go avec réseau sortant désactivé. Les commandes du modèle s’exécutent dans ce conteneur, qui ne reçoit ni clé API ni jeton GitHub en écriture. Les dépendances s’installent hors réseau depuis les wheels. Quarto reste vérifié par la CI séparée. Voir le shell hébergé de Responses.

Le client récupère uniquement le résultat final structuré et valide son contrat. Un autre job sur une machine fraîche utilise l’API Git pour publier les fichiers ; il n’exécute aucune commande du résultat. Douze fichiers texte et 60 Ko de JSON au plus peuvent être publiés par session. Les consignes, l’infrastructure et les métadonnées gelées du dataset ne sont pas modifiables par le modèle. Les figures peuvent être reproduites par du code et exportées en SVG ; les fichiers binaires ne transitent pas dans ce contrat.

Les ressources API créées par la session sont nettoyées. En cas d’interruption, l’upload est configuré pour expirer en une heure et le conteneur après vingt minutes d’inactivité. Un timeout connu demande l’annulation de la réponse ; si le réseau empêche sa confirmation, le contrôleur se met en pause.

3.4 Tickets, CI et continuité

Statut Utilisation
browt:ready Travail identifié BROWT et réalisable
browt:in-progress Session ou PR en cours
browt:blocked Ressource, décision ou preuve manquante
browt:state État durable du contrôleur

Les tickets sont dédoublonnés par clé stable, en tenant compte des tickets fermés. Seuls les tickets identifiés et écrits par le propriétaire ou GitHub Actions sont sélectionnés. Pour en ajouter manuellement, utiliser le marqueur <!-- browt-task:cle-stable --> dans le corps, le label browt:ready et des critères de fin explicites. Les issues publiques ordinaires ne lancent aucune session. Sans tâche prête, une planification peut proposer trois tickets au plus ; elle ne se répète pas tant que le backlog suivi reste inchangé.

Le premier travail scientifique disponible est le ticket nº 3 sur les groupes d’acquisition. Une étape partielle fusionnée laisse le ticket ouvert et prêt. Un blocage reste documenté. Seuls des critères déclarés achevés et une CI validée permettent une clôture automatique. La CI ne démontre pas la vérité d’une conclusion scientifique : les mesures et leurs entrées doivent rester consultables.

Le contrôleur demande explicitement la CI sur la branche. Il attend le bon workflow, la bonne branche et le SHA exact, revérifie la PR, puis tente une fusion verrouillée sur ce SHA. Il ne contourne aucune règle de branche et ne force aucun push. Après fusion, il demande explicitement Publish docs sur main. Les événements d’une PR créée par GITHUB_TOKEN peuvent demander une approbation GitHub distincte ; le run demandé est une vérification réelle supplémentaire. Voir les règles de déclenchement GitHub.

L’état persiste dans l’issue nº 8 : compteurs UTC, réservation, PR, révision, CI, sonde et raisons de pause. Les jobs sont sérialisés. Une interruption non finalisée provoque une pause, sans répétition d’un appel potentiellement facturé. Les fichiers non publiés d’un conteneur perdu ne sont pas récupérables.

Une PR en échec peut être réparée depuis sa dernière révision. Trois échecs de CI, un changement externe de la PR ou de main, ou une erreur de session API provoquent une pause. Après examen et correction, le mode resume efface la pause et la réservation incomplète, sans lancer de modèle. Une nouvelle exécution work est nécessaire. Une PR obsolète peut être fermée après conservation de son lien dans le ticket ; remettre le ticket prêt permet de repartir du nouveau main.

Le premier défaut de comparaison BASE…HEAD a été corrigé dans la PR nº 9 et sa pause d’initialisation levée par le contrôleur. Cette migration ne supprime aucune pause liée à une session de modèle.

3.5 Installation et premier essai

  1. Publier cette version du moteur Responses, vérifier sa CI et fusionner sa PR. Les pushes vers codex/autonomous-worker actualisent la PR d’infrastructure et ajoutent un lien sans doublon au ticket d’installation.
  2. Les trois secrets existants sont réutilisés : OPENAI_API_KEY, TELEGRAM_BOT_TOKEN et TELEGRAM_CHAT_ID. Aucune nouvelle clé n’est à transmettre.
  3. La politique de cette révision autorise une sonde unique avec les crédits déclarés et sans plan API payant déclaré. Après une CI réussie sur le SHA exact de main, le contrôleur réserve cette petite sonde, sans conteneur ni envoi de code. Un refus, une pause existante ou un drapeau d’arrêt explicite empêche une répétition automatique. Aucun travail scientifique n’est lancé par ce test.
  4. Vérifier le job de sonde, les tokens rapportés et probe_ok dans l’état durable. Le solde et l’origine du crédit restent vérifiables dans le compte. La sonde manuelle reste disponible via Actions → Autonomous research worker → Run workflow → main → probe, après configuration du drapeau de financement.
  5. Une fois l’accès établi, ajouter BROWT_API_BUDGET_CONFIRMED=true pour les sessions de travail. Pour le compte actuel, cette décision s’appuie sur les crédits éligibles et l’absence de plan API payant déclarés. Ce drapeau ne crée pas de plafond fournisseur. Un financement payant exige son propre contrôle de dépenses avant activation.
  6. Lancer manuellement le mode work. Vérifier la tâche, les commandes exécutées, la PR, sa CI et sa fusion. Ce cycle réel réussi met verified à true dans l’état.
  7. Ajouter enfin BROWT_AUTONOMY_ENABLED=true. Les appels horaires commencent seulement si la sonde et le premier cycle sont enregistrés comme réussis.

Les variables ordinaires se créent dans Settings → Secrets and variables → Actions → Variables. La variable facultative BROWT_API_MODEL choisit le modèle ; le défaut est gpt-6.2-sol. Sa disponibilité dépend de la clé. Les secrets restent dans l’onglet Secrets. Les droits du connecteur GitHub du chat et du jeton des workflows sont distincts.

La CI du nouveau moteur vérifie aussi le paquet exact de source et de dépendances dans une image Debian/Python 3.11, sans réseau et sans clé API. Les tests unitaires simulent les réponses ; ils n’utilisent aucun crédit du compte.

3.6 Cadence, arrêt et ressources

La cadence préparée est 07:17 et 19:17 UTC. GitHub peut retarder un déclenchement. Deux sessions de modèle par jour UTC sont autorisées au plus, sondes, planification, erreurs et réparations comprises. Le client borne les réponses en tokens et les appels d’outils ; son étape est limitée à douze minutes. Ces bornes ne garantissent pas un montant monétaire. Le crédit peut être épuisé ou expirer avant un renouvellement ; les erreurs ne déclenchent aucun achat.

Telegram reçoit au plus deux résumés utiles par jour UTC, en français, en une ou deux lignes. Le même message n’est pas répété. Un message peut attendre le jour suivant si le quota est épuisé. L’envoi est réservé avant la requête pour limiter les doublons ; un envoi interrompu à cet instant n’est pas répété automatiquement. GitHub conserve les détails et les preuves.

BROWT_AUTONOMY_ENABLED=false arrête les nouvelles sessions horaires. BROWT_API_BUDGET_CONFIRMED=false suspend aussi les appels manuels et les fusions automatiques. Un false explicite bloque aussi la sonde initiale. En dehors de cette sonde autorisée par la politique, l’absence de drapeau équivaut à false. Annuler un run déjà lancé peut rester nécessaire ; un drapeau ne peut annuler une requête partie. inspect reste utilisable sans appel au modèle.

L’archive réelle de 2 551 images reste locale. L’agent peut développer des outils sur fixtures, sans prétendre réévaluer ces images ou entraîner un détecteur dessus. Les données, poids, expériences NVIDIA et essais LDPlayer nécessiteront ensuite un environnement et un stockage adaptés, avec leurs propres preuves et budget.
