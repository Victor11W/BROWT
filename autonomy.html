3  Travail autonome et notifications

Installation, preuves et limites de l’exécution hébergée

3.1 État vérifié au 23 novembre 2026

Le socle de recherche est intégré dans main par la PR nº 6. La CI de main passe sur Ubuntu et Windows, Python 3.11 et 3.12, et rend le livre Quarto. La publication du livre et le déploiement Pages ont réussi.

Composant Preuve actuelle
Tickets de départ Quatre tickets publiés, nº 2 à 5
OpenAI Liste des modèles lue avec succès ; inférence Codex et financement encore non testés
Telegram Envoi distant réussi et réception confirmée par Victor
Worker Contrôleur, workflow et tests locaux préparés ; déploiement et premier essai réel à effectuer
Planification du modèle Désactivée tant que les conditions d’activation ne sont pas réunies
Dataset brut, GPU, émulateur Archive encore locale ; NVIDIA et LDPlayer absents du runner

Les résultats de l’amorçage sont dans ce run. Un contrôle de lecture OpenAI ne démontre pas une génération ou un budget disponible. Les tests du contrôleur utilisent une API simulée et ne prouvent pas une exécution Codex réelle. Les résultats scientifiques restent distincts de ces essais techniques.

3.2 Cycle d’une session

~{mermaid} flowchart TD S[“Déclenchement manuel ou horaire”] –> E[“Relire l’état et les tickets”] E –> G{“Budget et activation validés ?”} G –>|non| A[“Aucun appel au modèle”] G –>|oui| T[“Réserver une session et choisir un ticket”] T –> C[“Codex : une petite étape, code et preuves”] C –> V[“Contrôleur séparé : valider les fichiers retournés”] V –> P[“Branche et PR”] P –> I[“Research checks sur la révision exacte”] I –>|succès| M[“Fusion si les règles GitHub l’autorisent”] I –>|échec| R[“Réparation bornée ou pause”] M –> J[“Mettre à jour le ticket et l’état”] R –> J J –> N[“Bref message Telegram si utile”] ~

Le workflow Autonomous research worker est versionné dans .github/workflows/autonomous-worker.yml. Le contrôleur est dans .github/autonomy/worker.py ; les consignes et le schéma de résultat sont voisins.

Le modèle travaille sur un runner sans droits d’écriture GitHub et sans secret Telegram. Il renvoie des fichiers texte complets dans un objet JSON. Un autre job, sur une machine fraîche, valide ces données et utilise l’API Git pour publier. Aucune commande issue du résultat n’est exécutée par le contrôleur. Codex est la dernière étape de son job, conformément aux recommandations de l’action officielle.

Les fichiers d’infrastructure, les consignes d’agents et les métadonnées gelées du dataset ne sont pas modifiables par ce worker. Une modification de ces fichiers nécessite une PR d’installation examinée séparément. Le format texte limite une session à douze fichiers et 60 Ko ; les tâches plus grandes sont découpées. Les figures scientifiques peuvent être reproduites par des scripts et exportées en SVG ; les images binaires ne transitent pas dans ce contrat de session.

3.3 Tickets et continuité

Les tickets sont créés sans doublon grâce à des clés stables. Le contrôleur conserve les tickets fermés dans sa recherche de doublons. Il ne choisit que les tickets identifiés BROWT et écrits par le propriétaire ou GitHub Actions ; les issues publiques ordinaires ne lancent pas de session. Pour ajouter un ticket manuellement, le propriétaire peut utiliser le marqueur <!-- browt-task:cle-stable --> dans le corps et le label browt:ready ; la clé doit être stable et le ticket doit indiquer ses critères de fin.

Statut Utilisation
browt:ready Travail autorisé et réalisable sur le runner
browt:in-progress Une session ou une PR est en cours
browt:blocked Accès, matériel, décision ou preuve manquants
browt:state Issue technique contenant l’état durable du worker

Le premier ticket scientifique sélectionnable est le nº 3, consacré aux groupes d’acquisition. Le ticket de publication nº 2 n’est fermé qu’après vérification de la présence du socle dans main et du succès de sa CI. Le ticket d’autonomie nº 5 attend un cycle réel réussi. La baseline nº 4 reste bloquée tant que son protocole, les données accessibles au runner et le calcul nécessaire manquent.

Sans ticket prêt, une session de planification peut proposer au plus trois tâches. Elle ne se répète pas tant que le backlog suivi ne change pas. Les dépendances numériques sont vérifiées ; une tâche explicitement bloquée par une ressource ne devient pas prête simplement parce que ses autres dépendances sont closes.

Une PR partielle fusionnée remet le ticket au statut prêt. Un ticket n’est fermé que si le worker déclare ses critères achevés et si la CI de sa révision passe. La CI vérifie le code et le rendu, pas la vérité de chaque conclusion scientifique : les mesures réelles, leurs entrées et leurs scripts doivent rester consultables. Un résultat absent n’est jamais remplacé par une métrique inventée.

L’état est conservé dans une issue créée par le contrôleur, jamais dans le seul disque du runner. Il contient compteurs UTC, session réservée, PR, révision, CI, statut de la sonde et raisons de pause. Les jobs sont sérialisés. Après une interruption non finalisée, le worker se met en pause au lieu de répéter un appel potentiellement facturé. Les modifications non publiées d’un runner perdu ne sont pas récupérables ; le ticket et la réservation permettent de reprendre après examen du journal.

3.4 Installation et premier essai

  1. Publier puis fusionner la PR d’installation du worker, avec sa CI verte. Le push vers codex/autonomous-worker prépare cette PR automatiquement.
  2. Vérifier les trois secrets de dépôt déjà configurés : OPENAI_API_KEY, TELEGRAM_BOT_TOKEN et TELEGRAM_CHAT_ID. Aucune valeur ne doit apparaître dans le chat, un ticket, un commit ou un log.
  3. Dans Actions → Autonomous research worker → Run workflow, choisir main et le mode inspect. Cela initialise les statuts et l’état, sans appel au modèle.
  4. Le budget API approuvé est de 10 € par mois. Vérifier le financement compatible et le blocage effectif des dépenses avant tout essai facturable. Une fois ces contrôles établis, ajouter la variable de dépôt BROWT_API_BUDGET_CONFIRMED avec la valeur true. Cette variable est une autorisation, pas un plafond financier imposé par OpenAI.
  5. Lancer manuellement le mode probe. Il demande uniquement une réponse Codex, sans changement de fichier. Un succès prouve l’inférence à cet instant ; une erreur de crédits, modèle ou authentification provoque une pause.
  6. Lancer manuellement le mode work. Suivre le ticket, la PR, la CI explicitement déclenchée sur la branche et la fusion. Ne pas activer la récurrence avant d’avoir observé ce cycle complet. Le succès met verified à true dans l’état.
  7. Ajouter enfin BROWT_AUTONOMY_ENABLED=true dans les variables de dépôt. Le modèle ne sera appelé aux horaires prévus que si la sonde et le premier cycle sont aussi enregistrés comme réussis.

Les variables ordinaires se créent dans Settings → Secrets and variables → Actions → Variables. Les clés restent dans l’onglet Secrets. La variable facultative BROWT_CODEX_MODEL choisit le modèle ; vide, elle laisse le choix par défaut à Codex. Le modèle doit être disponible pour la clé configurée.

Les droits du connecteur GitHub du chat et ceux du GITHUB_TOKEN des workflows sont distincts. Le premier refuse actuellement les écritures. Cela ne démontre pas que le workflow manque de droits.

3.5 CI, fusion et erreurs

Une écriture faite avec GITHUB_TOKEN ne déclenche pas les mêmes événements qu’un push utilisateur. Le contrôleur appelle donc explicitement workflow_dispatch sur ci.yml. Il attend un run du bon dépôt, de la bonne branche et du SHA exact, puis vérifie à nouveau les fichiers et la cible de la PR avant fusion. La fusion utilise un SHA attendu et ne contourne aucune règle de branche. Après une fusion vérifiée du worker, le contrôleur déclenche explicitement Publish docs sur main pour actualiser le livre public. Le résultat de cette publication reste consultable dans son propre run. Voir les règles GitHub sur les déclenchements.

La CI de l’événement pull_request d’une PR créée par le bot peut rester en attente d’une approbation GitHub. Le run explicitement demandé est une vérification supplémentaire réelle, pas une approbation de ce bandeau. Si les règles du dépôt exigent une revue ou un autre contrôle, la fusion automatique s’arrête et le contrôleur signale la pause. Le premier cycle sert aussi à vérifier ce comportement.

Un échec de CI permet de reprendre la même PR depuis sa dernière révision. Après trois échecs distincts, la réparation se met en pause. Un changement externe de la PR ou de main provoque aussi une pause. Aucun force-push n’est utilisé. Une erreur de session Codex n’est pas relancée automatiquement.

Après examen et correction de la cause, lancer le mode resume efface la pause et la réservation incomplète ; ce mode ne lance aucun modèle. Une nouvelle exécution work est nécessaire. Une PR dont la base a changé exige une revue et une remise en cohérence avant reprise ; resume ne la rebase pas. Après revue, fermer la PR devenue obsolète libère son suivi ; conserver son lien dans le ticket, remettre ce ticket au statut prêt si nécessaire, puis utiliser resume et un nouveau work permet de repartir du nouveau main.

3.6 Cadence, coût et messages

Le budget autorisé par Victor le 23 novembre 2026 est de 10 € par mois pour l’API du worker BROWT. Il est consigné dans .github/autonomy/budget-policy.json. Ce fichier conserve la décision ; il ne mesure pas les coûts et n’impose pas de plafond au fournisseur. Le contrôle financier reste à vérifier dans le compte avant de passer BROWT_API_BUDGET_CONFIRMED à true. Si le compte utilise une autre devise, la conversion et une marge doivent être prises en compte. Même un blocage de dépense OpenAI peut présenter un léger dépassement pendant sa propagation : le seuil technique doit donc rester en dessous du budget autorisé.

Deux sessions quotidiennes sont un maximum ; le budget peut arrêter le travail plus tôt dans le mois. Aucun dépassement n’est autorisé par le choix de cette cadence.

La cadence préparée est 07:17 et 19:17 UTC. GitHub peut retarder un déclenchement. Le contrôleur autorise au plus deux sessions de modèle par jour UTC, en comptant les sondes, la planification, les réparations et les sessions interrompues. L’étape Codex est limitée à douze minutes. Relancer le même run n’autorise pas une seconde session ; il faut un nouveau déclenchement. Ces bornes limitent le travail effectué, sans garantir un montant maximal en euros ou dollars.

Les captures du compte indiquaient qu’aucun plan de facturation API payant n’était activé et n’affichaient pas de contrôle de dépense. Il reste à vérifier un financement compatible avec Codex avant l’essai. Des crédits liés à un abonnement ChatGPT peuvent avoir des restrictions : le bénéfice de crédits API ne couvre pas les usages Codex par clé API. Ne pas confondre accès au chat, accès à la liste des modèles, génération et financement du worker.

Un niveau de débit ou une alerte ne constitue pas un plafond de dépense. Consulter les limites de dépense OpenAI et vérifier le contrôle effectivement disponible dans le compte. Le GPU et les services externes demandent un budget distinct.

Telegram reçoit au plus deux messages utiles par jour UTC, en français, en une ou deux lignes : avancée intégrée, tâches préparées ou blocage. Le worker ne répète pas la même notification. Une notification différée peut attendre le jour suivant lorsque le quota est épuisé. Pour éviter les doublons après interruption, l’envoi est réservé avant la requête : un envoi perdu à cet instant n’est pas répété automatiquement. Telegram reste un résumé ; GitHub conserve les preuves et les détails.

Pour arrêter les nouvelles sessions horaires, passer BROWT_AUTONOMY_ENABLED à false. Pour suspendre aussi les appels manuels et les fusions automatiques, passer BROWT_API_BUDGET_CONFIRMED à false, puis annuler un run déjà lancé si nécessaire. La suppression d’une variable équivaut à false. Une variable ne peut pas annuler une requête déjà partie ; inspect reste disponible sans appel modèle.

3.7 Données et matériel

L’archive Roboflow de 2 551 images demeure hors Git, sur le PC de Victor. Le runner peut développer et tester des outils sur fixtures, mais ne peut pas réévaluer ces images ou entraîner un détecteur dessus sans un accès supplémentaire. Un stockage persistant avec empreintes et un protocole de récupération seront nécessaires. Aucun transfert de données, achat de calcul ou service payant supplémentaire n’est installé implicitement par le worker.

Les expériences NVIDIA et les essais LDPlayer nécessiteront ensuite une machine adaptée. Les tickets doivent rendre cette dépendance visible tout en permettant au travail CPU, aux analyses et aux visualisations reproductibles d’avancer.
